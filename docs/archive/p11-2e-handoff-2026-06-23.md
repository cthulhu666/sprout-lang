## Background: what P11-2e is

The typed-codegen path (`--use-ir-codegen`) is being made default, gated on
`scripts/ir_runtime_parity.sh` reaching zero typed failures (see `backlog.md:41-42`,
memory `project_pr11_typed_codegen_campaign`). P11-2e was the crash in
`checker.typecheck_typed`: `dict_from_list(builtin_entries() ++ extra)` SIGSEGVs in
`sprout_intern_hash` reading a garbage string key.

**Root cause:** `ir_rooting.op_produces_simple_heap` had no `IRMakeTuple` case, so
tuple-blob results from `sprout_alloc_tuple_blob` were never entered into `heap_origin`
and never rooted. Under GC they were collected mid-`analysis_entries`, corrupting the
`(key, scheme)` pairs.

## PR-B — the P11-2e fix (READY, do this SECOND)

### The change (one line)

In `stdlib/compiler/ir_rooting.sprout`, function `op_produces_simple_heap`, add after the
`IRMakeCtor` case (around line 80):

```
  # IRMakeTuple lowers to @sprout_alloc_tuple_blob — a heap pointer packed as
  # i64.  A tuple value held live across a later GC trigger must be rooted, so
  # its result enters heap_origin (P11-2e: unrooted (key, scheme) blobs in
  # dict_from_list were collected mid-function -> garbage key -> SIGSEGV).
  | sprout_ir.IRMakeTuple r _ -> Just(r)
```

**Do NOT also add `IRMakeTuple` to `op_triggers_gc`.** That was tried and reverted: it is
unmotivated by any failing test (added on symmetry with `IRMakeCtor` only), and by TDD
discipline must not ride here. If a future case needs "a value live across a bare tuple
build," it gets its own test + a separate change. (Blunt test: no current corpus file
roots a live value across a bare tuple construction.)

### Why it's correct at the campaign bar

- `range_and_intrinsics` (the P11-2e file) compiles+runs clean via `--use-ir-codegen`
  with this fix alone (13/13 pass at default threshold).
- The runtime correctly traces tuple blobs rooted via `push_i64_root`:
  `sprout_gc_mark_value` → `find_managed_ptr` → enqueues the `SPROUT_HEAP_TUPLE` node →
  `sprout_gc_drain_marks` traces its fields via `sprout_heap_child_count/value`
  (runtime `sprout_runtime.c` ~line 880/930/972/983). So rooting a tuple is mechanically
  sound — not a mis-trace.
- **Control proving default-threshold is the right bar:** under `SPROUT_GC_STRESS=1`,
  the *direct* build of `range_and_intrinsics` **also** SIGSEGVs (exit 139). So stress is
  stricter than the reference path itself meets; `range`'s stress-segfault is a shared
  direct+typed bug, **not** this PR's job.

### The regression test (already written, untracked)

`tests/stdlib/compiler/test_ir_tuple_result_rooting.spr` — mirrors P11-2d's
`test_ir_call_result_rooting.spr`. A deterministic IR-text differential: two
structurally-identical do-blocks differ only in whether the live-across-a-call local is a
tuple (`IRMakeTuple`, heap) or a scalar (`Int`). Pre-fix both emit equal
`sprout_gc_push_i64_root` counts; post-fix tuple > scalar. **Verified RED on unfixed
source, GREEN after the fix.** Keep it.

### Why PR-B can't land alone

Landing PR-B flips `test_ir_rooting` from (false-)green to red at the default threshold
(parity stays 9→9). Cause: correctly retaining tuples raises GC frequency, which
*surfaces* PR-A's latent UAF. So PR-A must land first. Confirmed: `count_substrs` IR is
**byte-identical** pre/post the IRMakeTuple fix (it's tuple-free), so PR-B does not
*cause* the flip — it *exposes* it.

## PR-A — the blocker (DO THIS FIRST; not yet solved)

### Symptom

`test_ir_rooting.spr`, compiled via `--use-ir-codegen`:
- default threshold: PASS (false green — GC-timing luck)
- `SPROUT_GC_STRESS=1`: CRASH (`str_len: invalid UTF-8 lead byte`)
- direct build under stress: PASS (correct reference)

### Minimal faithful repro (confirmed)

`fn walk(s: String, n: Int) -> Int = if n == 0 then str_len(s) else walk(s ++ "x", n-1)`,
called once before any `state` is allocated (no `state`-across-call confound). Typed
crashes under stress (`ref_read: not a Ref` — downstream heap corruption); direct passes.
Reproduce with the two `/tmp/min_apply2.spr`-style files (recreate; they were in `/tmp`).

### Root cause LOCATED (mechanism partially pinned)

Diff of `walk` direct vs typed IR:
- **Direct** roots the heap param `s` in a **persistent entry-level stack slot**
  (`alloca`+`push_i64_root` at function entry, popped only at return), and is **TCO'd**
  so each loop iteration re-`store`s the new string into that same rooted slot. The
  current `s` is therefore **always rooted**.
- **Typed** is plain recursion with **zero `push_i64_root` calls**. The heap `String`
  param `s` is never rooted; it appears only as a `str_concat` operand.

The typed rooting pass omits the root *by its model*: `s` is an operand of `str_concat`,
and the model assumes "operands are covered by the runtime `SPROUT_HANDLE` during the
call window" (see comment in `ir_rooting.sprout` lines ~14-17 / `test_ir_rooting.spr`
header). That assumption holds for an individual builtin (`str_concat` does
`SPROUT_HANDLE(h_left/h_right)` before `sprout_gc_maybe_collect_threshold`,
`sprout_runtime.c:3340-3342`) — but the aggregate behaviour still corrupts under stress,
and direct survives only via its **redundant** persistent entry-slot rooting.

### What is NOT yet known

The precise UAF path. Static analysis says every heap string in typed `walk` is either a
handle-protected operand or genuinely dead at each GC point — yet it crashes. **Five
theories ruled out by inspection** (do not re-chase these):
1. Tuple-blob mis-trace — runtime traces `SPROUT_HEAP_TUPLE` correctly.
2. Uninitialized tuple-blob window — `sprout_alloc_tuple_blob` doesn't zero-init, but
   this corrupts broadly, not one live string; not the symptom.
3. Push/pop imbalance — measured even (pre: 2975=2975, post: 3013=3013, module-wide).
4. `IRGetTupleField` extraction unrooted — backtrace refutes; corrupt value is a tuple-
   *free* `String` param, not a tuple-extracted value.
5. Closure-apply env unrooted — `walk`'s if/else lowers to a **plain branch**, not a
   captured-closure apply; no closure involved.

**Next step is lldb** (per advisor): watchpoint the swept object / catch who frees the
still-live string under stress. Do NOT tweak-and-refresh-seed in a loop hunting a sixth
static theory.

### Likely fix direction (a swing, not confirmed)

Make the typed path root heap-typed function parameters (and/or recursion-carried heap
values) persistently across the body, matching direct's conservatism. The rooting pass
already has param-seeding machinery (`seed_in_scope`, `params_heap_origin`; see
`test_ir_rooting.spr` test5 "heap param live across a trigger"). The question is why the
real typed path (`ast_to_ir`) doesn't seed/root `walk`'s `s`. **Confirm with lldb before
coding** — the empirical oracle is flipping `test_ir_rooting` CRASH→PASS under stress, NOT
an IR-shape match (that would encode an unconfirmed hypothesis).

### Acceptance / finish line for PR-A

- `test_ir_rooting` green under `SPROUT_GC_STRESS=1` **and** default.
- `range_and_intrinsics` unchanged (still passes default; its stress-segfault is out of
  scope — shared with direct).
- direct still passes stress.
- full `scripts/ir_runtime_parity.sh` net-positive, no new reds.

1. **Behavioral GC-stress pass** — e.g. `just test-stress` re-running a curated subset of

   oracle AND closes the campaign-wide false-green blind spot. (There is currently **no**
   `SPROUT_GC_STRESS` usage anywhere in `justfile`/`scripts/`.)
2. **Deterministic IR-assertion** — a default-threshold test asserting the now-confirmed
   fix shape (mirrors `test_ir_rooting.spr`'s IR-text checks). Add this *after* lldb
   confirms the mechanism, so it encodes a verified shape.

## Operational notes / gotchas (cost-savers)

- **No GC-stress in CI** — bugs in this class only show under `SPROUT_GC_STRESS=1`.
  Always stress-test typed-codegen rooting changes manually until the stress pass lands.
- **Linking needs frameworks:** `clang <ir.ll> runtime/sprout_runtime.c -O2
  -framework Security -framework CoreFoundation -o <bin>` (the runtime now has TLS/HTTP
  deps). Without them: `Undefined symbols: _SSLCreateContext` etc.
- **Compiler-source change order:** `rm -f build/compile_driver_bin_stage1` (mtime trap,
  memory `feedback_refresh_seed_stale_binary`) → `refresh-seed` (memwatch) **before**
  `just test` (memory `feedback_refresh_seed_before_test_for_compiler_changes`).
  refresh-seed ≈ 105s, full `just test` ≈ 245s, full parity ≈ 527s.
- **`--use-ir-codegen` uses the seed-built binary's own codegen**, so a source change to
  the rooting pass only takes effect after refresh-seed. (A library-level test that
  imports `ir_pipeline` recompiles from working-tree source and reflects changes
  immediately — that's why PR-B's regression test could be verified without refresh-seed,
  but end-to-end `--use-ir-codegen` repro needs the refreshed seed.)
- **Bash hooks** block `cat`/`head`/`tail`/`sed`/`awk` with file args — use Read, or
  `grep`/`cut` pipeline filters.
- **Diagnostic oracle:** `SPROUT_GC_STRESS=1` collapses the timing window and reveals
  false greens. `SPROUT_GC_THRESHOLD=<huge>` does **NOT** disable the collector (it still
  fires with reason "threshold") — do not use it as a "GC off" technique.
