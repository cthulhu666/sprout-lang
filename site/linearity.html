Linear Types in Sprout

Part I explains linear types: what they check, why a functional language wants them, and the ideas built on them (borrowing, closure promises, in-place updates). Part II shows how to write each idea in Sprout. It assumes you know immutable data, pattern matching and higher-order functions.

Part I · The ideas

Code in this part is pseudo-code. Part II has the real syntax.

1What sharing costs

In a pure language a value never changes. That is why you can share it freely: pass it to ten functions, keep it in three lists, and nobody can surprise anybody. It is also why you can replace an expression by its value without changing the program.

Free sharing has two costs.

Updates copy. "Setting" one element of an immutable array must build a new array, because someone may still hold the old one and expect the old value. So one write to an array of n elements costs n, not 1. A loop that writes every element does n² work instead of n.

Resources get two owners, or none. Some values stand for something that must be finished exactly once: a file to close, a connection to close, a task to join. If such a value can be shared, two parts of the program can both close it. If it can be dropped, nobody closes it, and the program runs until it is out of file descriptors.

Both costs have one cause. The compiler does not know how many references to a value exist. If it knew there was exactly one, the update could happen in place (no one else can see the change), and the resource would have exactly one owner who must finish it. Linear types give the compiler that knowledge.

2Copy and drop

An ordinary type system lets you do two things with a variable that you rarely notice:

  • Drop it: never use it. k(x, y) = x drops y. Logicians call this weakening.
  • Copy it: use it twice. dup(x) = (x, x) copies x. Logicians call this contraction.

Type systems that restrict these rules are called substructural. Taking away one rule or both gives four disciplines:

disciplinemay dropmay copya value is used
unrestricted (ordinary types)yesyesany number of times
affineyesnoat most once
relevantnoyesat least once
linearnonoexactly once

"No copy" stops the double close. "No drop" stops the leak. A language that runs a destructor whenever a value is dropped can allow drops, because the destructor does the closing. A language without destructors has to forbid drops, so the programmer closes the file on every path. That is the linear row.

What counts as a "use"? Any mention of the name: passing it to a function, matching on it, returning it. A match that throws the value away (a wildcard pattern) mentions it but drops it, so it must be rejected too. The count is taken on every path through the function. If an if uses a value in one branch, every branch must use it:

This forces you to decide what happens to the file on every path. That decision is the point.

3Linear functions or linear types

There are two places to put the rule, and they mean different things.

On the function. A function promises to use its argument exactly once. The value itself is not special: the caller may still share it, and call the function twice on it. The promise is about the future, and only about that one function.

On the type. A type is declared linear, and every value of it is linear from the moment it is built. Every function, every let, every branch must treat it as used-once. Then nobody can ever make a second reference to it. So at the point a value is used, its user holds the only reference. This is called uniqueness: a guarantee about the present, not a promise about the future.

Uniqueness is what makes in-place updates safe, as the end of this part shows. It is also what you need for resources: a file that nobody else can hold has exactly one owner.

4Threading: pass it on, get it back

If every use consumes a value, how do you do two things with it? You return it. A function that changes a linear value takes it and returns the new one. The caller uses that one exactly once, by passing it to the next step:

f1 = open(1)
f2 = bump(f1, 10)     # f1 is used up; only f2 exists now
f3 = bump(f2, 100)
close(f3)

This is called threading. Since the old value can never be used again, nobody can tell the difference between "a new value" and "the same value, changed". The code stays pure: each function still maps inputs to outputs. Linearity adds only a proof that the old input is dead.

5Borrowing: look without using up

Threading is clumsy for reads. Asking an array its length should not consume the array, and returning it from every read adds noise. So linear systems add borrowing: a use that reads the value but leaves the owner responsible for it. The owner can lend the value many times, and still owes its one real use.

The danger is a borrow that is still in use after the owner consumes the value: a read of a file that is already closed. Three rules prevent it:

  1. No borrow after the consume. close(f); peek(f) is rejected.
  2. A borrow lasts the whole call. In both(f, f), if the first argument is borrowed and the second consumed, the callee could read the first after closing the second. So a value lent to a call may not be consumed by the same call.
  3. A borrow cannot escape. A function that borrows a value may not return it, store it, or release it. Returning it would hand the caller a second owner.

Rule 3 is a strong limit, and it buys simplicity. A borrow can only be passed down, into calls, so it always ends when the call that received it returns. The compiler never needs to track how long a borrow lives. Values with this limit are called second-class.

Records. Reading a field is a use of the whole record. So an owned linear record can give up only one field. To read several, borrow the record.

6Linear values inside other values

Maybe File is not a linear type: Nothing holds no file. But dropping a Just drops the file inside it. So the checker must track any value whose type contains a linear type, as a type argument, a tuple part or a field. The same rules apply to it: use it once, on every path.

Two edges of this rule:

  • A function type is not a container. Unit -> File is a recipe for a file, not a file. Dropping the recipe leaks nothing.
  • A global cannot hold a linear value. Every function in the module can name a global, so no single scope can use it once.

7Generic code

Take dup(x: a) = (x, x). For Int it is fine. For a file it makes two owners. So a language must decide: may a type variable stand for a linear type?

There are two defaults:

  • Yes, by default. Then every generic function must be written as if its type variables were linear, and one that copies or drops must say so.
  • No, by default. A type variable stands only for types that hold no linear value, and a generic function that is careful opts in.

The second default fits functional code better. Much generic code copies or drops on purpose: const(x, y) = x drops y, and an equality test over a list stops at the first difference without looking at the rest. With the first default all of that code would need annotations.

The opt-in must be checked, not trusted. A function that says "I use my a once" has its body checked as if a were linear. Otherwise the opt-in would be a way to smuggle a copy through.

8Closures: how often, and how long

Closures are where linear types get hard. A lambda that captures a linear value carries it. Two questions about the lambda then matter, and neither is visible where the lambda is written. Only the function that receives it knows:

  • How often will it run? A closure that consumes a captured file and runs twice closes it twice. A closure that never runs never closes it.
  • How long will it live? A closure that only reads a borrowed file may run many times. But if it is stored and runs after the owner closes the file, it reads a closed file.

So the receiving function makes promises about its function parameter, and the compiler checks them in its body. One promise per question:

the callee promisesso the caller's lambda may
nothingcapture nothing linear
"I call it at most once"move a linear value in; it is consumed when the closure runs
"I don't keep it past the call"borrow a value; the closure ends before the owner can consume it
bothmove in and borrow

Note "at most once", not "exactly once". A callee that never calls the closure keeps its promise, and a value moved into that closure is never consumed. "Exactly once" would need the compiler to prove the call happens, which it cannot do in general. So a library that runs closures, such as a task scheduler, must also guarantee at run time that they run.

A lambda's own parameter. A lambda may take a linear value as its parameter if it only borrows it. This gives the with-resource pattern: a helper opens a file, lends it to your lambda, and closes it afterwards, so you cannot forget the close. A lambda that consumes its parameter is harder: the callee may call it zero times or many, so nothing proves each value it is given gets consumed once. A named function does not have this problem, because it is checked on its own.

9In-place updates

An update copies only because someone else may still hold the old value. If the compiler knows nobody does, the update can happen in place. There are two ways to know that.

  • At run time, by counting references. Each object carries a counter, and each update checks it: a count of one writes in place, anything else copies. The price is the counter, the check, and a copying slow path.
  • At compile time, from linear types. A value of a linear type is unique, so the proof is in the types. No counter and no check.

The compile-time proof gives two things.

A linear array

Put the ideas together and you get an array with pure operations and in-place writes:

  • Reads borrow the array, so they don't use it up.
  • Writes consume it and return it, so the array is threaded from one write to the next. After a write, nothing can name the old array, so nobody can see that the write changed it. The write costs 1, not n.
  • Freeze turns it into an ordinary shared array without copying, since nothing else holds it. After that it is immutable and may be shared again.

The program that would break purity reads the old version after a write:

w   = set(0, 1, v)
old = get(0, v)       # if this compiled, it would see the new value

That is exactly a use after consume, so the type system rejects it. The in-place write stays invisible.

Threading the array through every single write is noise when a loop writes many cells. A bulk operation takes a list of writes and applies them in one call, so the array is threaded once per batch.

Reusing a cell

The fact behind the array holds for every linear type: a consumed linear value has no other reference. So when a function takes a linear value apart and builds a new value of the same shape, the new one can be written into the old one's memory instead of allocated. A tree insert that rebuilds the path to a new key then allocates only the new node. Code written as pure updates runs as mutation.

One limit: the value must be owned, not borrowed. A borrowed value's owner still holds it.

Part II · In Sprout

Sprout puts linearity on the type, so every value of a linear type is unique, and it uses that to update values in place. Each example below was compiled inside a full program.

10Linear types

Write linear after type (or after wrap). Here is a toy file handle used through the rest of this part. It wraps an Int, and close returns that number so the examples have something to print:

compilesA linear type and its life
type linear File = File Int

fn open(n: Int) -> File = File(n)

fn close(f: File) -> Int =
  match f with
  | File n -> n

fn main() -> Unit !{IO} = print(close(open(3)))
output 3

The checker rejects the three mistakes: a copy, a drop, and a drop on only one path.

rejectedCopy: closing twice
fn twice(f: File) -> Int = close(f) + close(f)
error linear value 'f' is used more than once (linear values must be used exactly once)
rejectedDrop: forgetting to close
fn forget(f: File) -> Int = 0
error linear value 'f' is never used (linear values must be used exactly once)
rejectedA drop on one path
fn maybe_close(f: File, b: Bool) -> Int = if b then close(f) else 0
error linear value 'f' is used in some branches but not others (every branch must use it exactly once)

To change a file, take it and return the new one. bump does that, and the file is threaded through two calls:

compilesThreading through two steps
fn bump(f: File, x: Int) -> File =
  match f with
  | File n -> File(n + x)

fn main() -> Unit !{IO} = print(close(bump(bump(open(1), 10), 100)))
output 111

11borrowing

To read a value without using it up, mark the parameter borrowing. The function may read it as often as it likes, and the caller still owes the one real use:

compilesRead twice, then close
fn peek(f: borrowing File) -> Int =
  match f with
  | File n -> n

fn report(f: File) -> Int =
  let a = peek(f)
      b = peek(f)
  in a + b + close(f)
output 15 # report(open(5))

The three borrow rules, as errors:

rejectedRule 1: a borrow after the consume
fn late(f: File) -> Int =
  let n = close(f)
  in n + peek(f)
error linear value 'f' is used after it was consumed
rejectedRule 2: borrowed and consumed in one call
fn both(b: borrowing File, c: File) -> Int = peek(b) + close(c)

fn main() -> Unit !{IO} =
  let f = open(1)
  in print(both(f, f))
error 'f' is borrowed by another argument of this call and cannot be consumed in it: the callee holds the borrow for the whole call, so it could read 'f' after consuming it
rejectedRule 3: returning a borrow
fn give_back(f: borrowing File) -> File = f
error 'f' is a borrowing parameter and cannot be consumed; take it `consuming` if this function should release it

An unmarked linear parameter is owned. consuming spells that out, if you want it visible in an API. Borrowing costs nothing at run time.

Records

rejectedTwo fields of an owned record
type linear Pos = (x: Int, y: Int)

fn sum_owned(p: Pos) -> Int = p.x + p.y
error linear value 'p' is used more than once (linear values must be used exactly once)
compilesBorrow to read, then finish it
fn sum_borrowed(p: borrowing Pos) -> Int = p.x + p.y

fn finish(p: Pos) -> Int = p.x

fn total() -> Int =
  let p = Pos(x = 1, y = 2)
      s = sum_borrowed(p)
  in s + finish(p)
output 4

The standard library uses this shape. stdlib.net's TcpConnection is linear: reads and writes borrow it, and close consumes it.

12Containers

A value that holds a linear value is tracked too. A Maybe File must be settled in both cases:

rejectedDropping a Maybe File
fn lose(m: Maybe File) -> Int = 0
error linear value 'm' is never used: its type `Maybe File` contains the linear type `File` (linear values must be used exactly once)
compilesSettle both cases
fn settle(m: Maybe File) -> Int =
  match m with
  | Just f -> close(f)
  | Nothing -> 0
rejectedA module-level file
let shared = open(1)
error top-level `let` 'shared' holds a linear value (`File`): every function can use a module binding, so it cannot be used exactly once; create the value inside a function and pass it on

_ drops what it matches

Matching a value counts as its use, so a _ pattern that matches linear content would leak it. Such a _ is rejected, whether it is a whole arm (also let _ = e) or sits inside a constructor or a tuple:

rejectedA wildcard arm
fn sneaky(f: File) -> Int =
  match f with
  | _ -> 0
error `_` drops a linear value of type `File` without consuming it. Bind it and pass it on, or match its constructor and consume its linear fields.
rejectedA wildcard over a linear field
type Wrap = | Wrap File

fn sneaky2(w: Wrap) -> Int =
  match w with
  | Wrap _ -> 0
error `_` drops a linear field of type `File`. Bind it, as in `Wrap c`, and consume it.

A _ that can only match linear-free cases is fine. So is a _ over a borrowed value, which consumes nothing:

compilesEarlier arms took the file; a borrow drops nothing
type Slot = | Filled File | Blank

fn empty_out(s: Slot) -> Int =
  match s with
  | Filled f -> close(f)
  | _ -> 0              # only Blank is left

fn tag(f: borrowing File) -> Int =
  match f with
  | _ -> 1

Swap the arms (| Blank -> 0 | _ -> 1) and the _ can match a Filled, so it is rejected.

13where linear

In Sprout a type variable stands only for types that hold no linear value. So dup compiles, and the call that would copy a file is rejected:

rejecteddup(open(1))
fn dup(x: a) -> (a, a) = (x, x)

fn main() -> Unit !{IO} =
  match dup(open(1)) with
  | (a, b) -> print(close(a) + close(b))
error `dup` takes `a` as a value it may copy or drop, and `File` is linear; if `dup` uses its `a` exactly once, add `where linear a` to it

Opt in with where linear a. The function then accepts linear and ordinary types alike:

compilesAn opt-in generic function
fn ident(x: a) -> a where linear a = x

fn main() -> Unit !{IO} = print(close(ident(open(1))) + ident(2))
output 3
rejectedThe opt-in is checked
fn dup(x: a) -> (a, a) where linear a = (x, x)
error linear value 'x' is used more than once (linear values must be used exactly once)

The prelude's list_fold carries where linear a, linear b, so a fold's accumulator may be linear.

14once and local

A function that takes a closure states its promises as a mode on that parameter:

parameterpromisethe caller's lambda may
g: A -> Bnonecapture nothing linear
g: once A -> Bcalled at most oncemove a linear value in
g: local A -> Bnot kept past the callborrow a linear value
g: once local A -> Bbothboth

Without a promise, a capture is rejected:

rejectedMoving a file into an ordinary lambda
fn run(g: Unit -> Int) -> Int = g(())

fn main() -> Unit !{IO} =
  let f = open(7)
  in print(run(\_ -> close(f)))
error linear value 'f' captured by a lambda is not yet supported (higher-order linearity is deferred; if the callee invokes this closure at most once, declare that parameter `once`)

once

compilesA move into a once closure
fn run_once(g: once Unit -> Int) -> Int = g(())

fn main() -> Unit !{IO} =
  let f = open(7)
  in print(run_once(\_ -> close(f)))
output 7
rejectedBreaking the promise
fn run_twice(g: once Unit -> Int) -> Int = g(()) + g(())
error `once` parameter 'g' is used more than once: declaring it `once` promises callers this function invokes it AT MOST once, and that promise is what licenses them to move a linear value into the closure they pass

stdlib.task's task_spawn(scope, work: once Unit -> Unit !{IO}) is how a server moves each accepted connection into the task that handles it. with_scope joins its tasks, which is the run-time guarantee that they run.

local

compilesLending a file to a local closure
fn sum_with(g: local Int -> Int, xs: List Int) -> Int =
  match xs with
  | [] -> 0
  | [x | rest] -> g(x) + sum_with(g, rest)

fn total(f: File) -> Int =
  let n = sum_with(\x -> x * peek(f), [1, 2, 3])
  in n + close(f)
output 14 # total(open(2)): 2 + 4 + 6, then close returns 2
rejectedA local parameter that escapes
fn keep(g: local Int -> Int) -> Int -> Int = g
error `local` parameter 'g' may outlive the call: returned or stored. Declaring it `local` promises callers it does not, and that promise is what lets them lend it borrowed values

The prelude's concrete combinators take their function local: list_fold, list_map, list_each, the vec_, range_ and result_ families, and the Foldable functions. So a fold can read a borrowed value:

compilesBorrowing inside list_fold
fn total(f: File) -> Int =
  let n = list_fold(\ (acc, x) -> acc + x * peek(f), 0, [1, 2, 3])
  in n + close(f)
output 14 # total(open(2))

The class methods map, filter, and_then and traverse do not take local, because some instances (a parser, a state monad) keep the function. Use list_map and friends when a lambda must borrow:

rejectedBorrowing inside the class method map
fn scaled(f: File) -> Int =
  let ys = map(\x -> x * peek(f), [1, 2, 3])
  in list_length(ys) + close(f)
error borrowed value 'f' captured by a lambda is not yet supported (…); or, if the callee is your own and does not keep this closure past the call, declare that parameter `local`, as the prelude's concrete `list_`, `vec_`, `range_` and `result_` functions and the `Foldable` functions do; the class methods `map`, `filter`, `and_then` and `traverse` do not

With-resource

Write the lambda's parameter type as (borrowing File) -> Int. A plain \c -> … in that slot is read as borrowing:

compilesA with-resource helper
fn with_file(n: Int, work: (borrowing File) -> Int) -> Int =
  let f = open(n)
      r = work(f)
  in r + close(f)

fn main() -> Unit !{IO} = print(with_file(3, \c -> peek(c) * 10))
output 33

A lambda that consumes its parameter is rejected. A named function in the same slot is accepted: with_file2(3, close) compiles.

rejectedA lambda that consumes its parameter
fn with_file2(n: Int, work: File -> Int) -> Int = work(open(n))

fn main() -> Unit !{IO} = print(with_file2(3, \c -> close(c)))
error consuming linear lambda parameter 'c' is not yet supported (higher-order linearity is deferred: the closure may run 0..n times, so the value cannot be proved consumed exactly once); take it `borrowing` if this lambda only reads the value

15LinVec

stdlib.linvec provides the linear array: reads borrow it, and writes consume it and return it. It is a wrap linear over the runtime vector, and its constructor is not exported, so only the module can build one or take one apart. Import the type, and call the functions through the module:

import stdlib.linvec (LinVec)
import stdlib.linvec as linvec

linvec.new(n: Int, x: a) -> LinVec a                     # n copies of x
linvec.empty() -> LinVec a
linvec.from_list(xs: List a) -> LinVec a
linvec.get(i: Int, v: borrowing LinVec a) -> Maybe a     # Nothing out of range
linvec.set(i: Int, x: a, v: LinVec a) -> LinVec a        # consumes v, returns it
linvec.push(x: a, v: LinVec a) -> LinVec a               # amortised O(1)
linvec.pop(v: LinVec a) -> (Maybe a, LinVec a)           # the last element and the rest
linvec.length(v: borrowing LinVec a) -> Int
linvec.freeze(v: LinVec a) -> Vec a                      # no copy; ends its life
linvec.drop(v: LinVec a) -> Unit
linvec.scatter(is: List Int, x: a, v: LinVec a) -> LinVec a
linvec.accum(f: local a -> b -> a, pairs: List (Int, b), v: LinVec a) -> LinVec a

A linvec.set costs the same at any size and allocates nothing. The copying vec_set on a Vec costs time in proportion to the vector's length.

A sieve

compilesPrimes below a million, pure
import stdlib.linvec (LinVec)
import stdlib.linvec as linvec

# Cross out multiples of p, from p*p up to n.
fn cross_out(i: Int, p: Int, n: Int, marks: LinVec Bool) -> LinVec Bool =
  if i > n then marks
  else cross_out(i + p, p, n, linvec.set(i, true, marks))

fn sieve(p: Int, n: Int, marks: LinVec Bool) -> LinVec Bool =
  if p * p > n then marks
  else
    let Just crossed = linvec.get(p, marks) else marks
    in if crossed then sieve(p + 1, n, marks)
    else sieve(p + 1, n, cross_out(p * p, p, n, marks))

fn count_primes(n: Int) -> Int =
  let marks = linvec.freeze(sieve(2, n, linvec.new(n + 1, false)))
  in list_length([p for p in 2..n if vec_get(p, marks) == Just(false)])
output 78498 # count_primes(1000000)

marks is used once on every path. The let … else marks line borrows it, then either returns it or passes it on.

Loops

Reading inside a fold works, since list_fold takes its function local:

compilesBorrowing a LinVec inside list_fold
fn weighted(grid: borrowing LinVec Int, xs: List Int) -> Int =
  list_fold(\ (acc, i) -> acc + maybe_with_default(0, linvec.get(i, grid)), 0, xs)
output 16 # grid [1, 5, 1, 5], xs [0, 1, 3, 3]

Writing from a fold's lambda does not, because the lambda would consume its parameter:

rejectedA set inside a fold's lambda
fn fill(v: LinVec Int) -> LinVec Int =
  list_fold(\ (acc, i) -> linvec.set(i, 1, acc), v, [0, 1, 2])
error consuming linear lambda parameter 'acc' is not yet supported (higher-order linearity is deferred: the closure may run 0..n times, so the value cannot be proved consumed exactly once); take it `borrowing` if this lambda only reads the value

Use a named step function, a recursive loop (as in the sieve), or a bulk operation:

compilesA named step function
fn mark(v: LinVec Int, i: Int) -> LinVec Int = linvec.set(i, 1, v)

fn fill(v: LinVec Int) -> LinVec Int = list_fold(mark, v, [0, 2])
output 1 0 1 0 # fill(linvec.new(4, 0)), frozen
compileslinvec.scatter and linvec.accum
fn histogram(xs: List Int) -> Vec Int =
  linvec.freeze(linvec.accum(\ (count, one) -> count + one,
                             [(x, 1) for x in xs], linvec.new(4, 0)))

# linvec.freeze(linvec.scatter([0, 2, 4], 9, linvec.new(5, 0)))
# histogram([1, 3, 1, 0, 1])
output 9 0 9 0 9 1 3 0 1

linvec.accum's function works on elements, not on the array, so it is an ordinary lambda. A write out of range stops the program. A read out of range is Nothing.

Growing and shrinking

push appends, doubling the storage when it is full. pop returns the last element with the rest, and an empty vector comes back unchanged with Nothing. The rest is linear, so it must still be consumed:

compilesPush four squares, pop them all
fn squares(i: Int, n: Int, v: LinVec Int) -> LinVec Int =
  if i > n then v else squares(i + 1, n, linvec.push(i * i, v))

fn total(acc: Int, v: LinVec Int) -> Int =
  match linvec.pop(v) with
  | (Just x, rest) -> total(acc + x, rest)
  | (Nothing, rest) -> let _ = linvec.drop(rest) in acc

# total(0, squares(1, 4, linvec.empty()))
output 30

stdlib.linheap builds a pure binary min-heap on these: wrap linear LinHeap a = LinVec a, with push and pop in amortised O(log n) and peek and size borrowing. It drains the same way:

compilesHeap sort with LinHeap
import stdlib.linheap (LinHeap)
import stdlib.linheap as linheap

fn drain(acc: List Int, h: LinHeap Int) -> List Int =
  match linheap.pop(h) with
  | (Just x, rest) -> drain(Cons(x, acc), rest)
  | (Nothing, rest) -> let _ = linheap.drop(rest) in list_reverse(acc)

# drain([], linheap.from_list([5, 1, 4, 2, 3]))

16Reuse

Cell reuse needs no new syntax. When a function matches an owned linear parameter and builds a value of the same type with the same number of fields, the compiler writes it into the old cell:

compilesA linear tree; each rebuilt node reuses its cell
type linear Tree = | Leaf | Node Tree Int Tree

fn insert(k: Int, t: Tree) -> Tree =
  match t with
  | Leaf -> Node(Leaf, k, Leaf)
  | Node l v r ->
      if k < v then Node(insert(k, l), v, r)
      else if k > v then Node(l, v, insert(k, r))
      else Node(l, v, r)

fn add(t: Tree, k: Int) -> Tree = insert(k, t)

fn to_list(t: Tree, acc: List Int) -> List Int =
  match t with
  | Leaf -> acc
  | Node l v r -> to_list(l, Cons(v, to_list(r, acc)))

# to_list(list_fold(add, Leaf, [72, 88, 72, 95, 61]), Nil)
output 61 72 88 95

This is the ordinary pure insert; only the word linear is new. On a million inserts it runs about 2.3× faster than the same tree without linear, and allocates about 40× fewer objects: one per new key, instead of one per node on every path.

Reuse applies when the matched value is an owned parameter of the function. The new value must have the same type and the same number of fields.

17Where it stops today

Linear types are Experimental (spec §5.8). The first three limits are rejected with an error that names them. The last two compile, and the spec lists them as known gaps.

Consuming in a lambda

A lambda that consumes its own parameter is rejected, and so is capturing a linear value at a parameter with no promise. Use a named function, recursion, or a bulk operation.

The class methods map, filter, and_then, traverse

They take no local. Use the concrete list_/vec_ functions when a lambda must borrow.

Records with several linear fields

rejectedReading one linear field drops the other
type linear Pair = (a: File, b: File)

fn first(p: Pair) -> Int = close(p.a)
error reading `a` consumes `p` and drops its linear field `b`; use a constructor type and `match` it to take every linear field

Known gaps

  • A channel abandoned while it still holds linear values is not reported.
  • Cancelling a task scope, or a with_timeout that expires, drops a waiting task without finishing its closure. A linear value it held is never released. Lending to a with_timeout body is safe: you keep ownership and release the value yourself.

18Error cheat sheet

is used more than once
You consumed it twice. Make the earlier uses borrowing, or thread it: have the first function return the value.
is never used
Some path forgets it. Close it, freeze it, drop it, or return it.
is used in some branches but not others
Consume it in every branch, or once before the if/match.
is used after it was consumed
Move the read before the consume, or read the new value the consuming call returned.
is borrowed by another argument of this call
Split the call: do the borrow in a let first, then consume.
is a borrowing parameter and cannot be consumed
The function releases or returns a value it only borrowed. Take it owned, or stop returning it.
takes `a` as a value it may copy or drop
The generic function was not written for linear values. If it uses its argument exactly once, add where linear a. If not, it really would copy or drop it.
captured by a lambda is not yet supported
For a move, the callee's parameter must be once. For a borrow, it must be local. Otherwise read the value before the lambda and capture the result.
consuming linear lambda parameter
Use a named function, a recursive loop, or a bulk operation (linvec.scatter, linvec.accum).
`_` drops a linear value / field
Bind the value or field to a name and consume it. A _ is fine over a borrowed value, or where earlier arms already took every case that holds linear content.
`local` parameter may outlive the call
Your function returns, stores or passes on its local parameter somewhere that is not local. Drop the local, or stop keeping the closure.
drops its linear field
Declare the type with a constructor and match it, which takes every field at once.
